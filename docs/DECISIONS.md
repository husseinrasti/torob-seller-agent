# Decisions & deviations from the spec

One line per deviation from `docs/01-master-build-spec.md`, with the reason.

| # | Milestone | Decision | Reason |
|---|---|---|---|
| 1 | M0 | Docker base image `node:22-alpine` instead of `node:20-alpine`; CI on Node 22. | `ai@7`, `@ai-sdk/*@4` and `@openrouter/ai-sdk-provider@3` declare `engines.node >= 22` (Node 20 is EOL). |
| 2 | M0 | Vercel AI SDK **v7** (latest stable, `ai@7.0.148`) instead of v5. `stepCountIs` is kept (v7 alias of `isStepCount`); structured output uses `generateText({ output: Output.object(...) })` instead of `generateObject`. | Kickoff asks for latest stable; `generateObject` is the legacy API in v7. |
| 3 | M0 | `postgres:16-alpine` image. | Same major version and contrib extensions (pg_trgm, unaccent), smaller image. |
| 4 | M0 | Host ports are configurable: `DB_PORT` (db), `HTTP_PORT`/`HTTPS_PORT` (Caddy), `PORT` for `pnpm dev` (default 3010). | Dev machine already uses 5432/3000/80; defaults stay 5432/80/443 on a VPS. |
| 5 | M0 | Inside the container, migrate/seed run as esbuild bundles: `node scripts/migrate.cjs`, `docker compose run --rm app node scripts/seed.cjs` (instead of `pnpm migrate` / `pnpm seed`). | The Next standalone runtime image has no pnpm/tsx/devDependencies; bundles keep the image small and non-root. |
| 6 | M0 | Empty optional env vars (e.g. `OPENAI_BASE_URL=`) are deleted at startup (`instrumentation.ts`, `scripts/load-env.ts`). | `@ai-sdk/openai` throws "baseURL must be a non-empty string" at import time when the var is an empty string. |
| 7 | M0 | `video/` (challenge recording) is git-ignored. | Not part of the code submission; large binary. |
| 8 | M0 | GitHub repo created with `gh repo create` (spec §10.1 says the owner creates it). | The owner's kickoff message explicitly asks for `gh repo create … --public` when `gh` is authenticated. |
| 9 | M0 | shadcn/ui v4 CLI (`radix-nova` preset, `--rtl`), which imports `cn` from the `cn` package. | Current shadcn generator; RTL support is built in. |
| 10 | M1 | Extra derived columns: `shops.unit_kind`, `shops.installment_in_person`, `shops.torobpay_in_person`, `products.brand_display`, `products.offer_count`, `offers.has_warranty`, `followups.question`, `followups.due_at`. | UI needs «واحد/پلاک», the payment channel («حضوری تأییدشده» vs «اعلام‌شده»), a display brand (75% of `brand_name` is null → inferred from titles), and a due time for simulated replies. |
| 11 | M1 | All derivations (normalization, mall, hours, quality, aggregates) are computed in TypeScript during 4 streaming passes and loaded with `COPY` — no post-load `UPDATE`s. | 35 s total seed on a laptop; avoids rewriting 225k wide product rows and their GIN indexes. |
| 12 | M1 | `unit_label` is stored with ASCII digits (UI renders Persian digits); `mall_key` uses Persian digits («علاءالدین ۲») as in the spec examples. | Consistent querying; matches the acceptance checks. |
| 13 | M1 | `DATASET_AS_OF` is interpreted as the end of that day in Tehran. | A price changed on the snapshot day is «امروز» (0 days), never negative. |
| 14 | M1 | Acceptance (a): `product_d24b597176bdf2a82035dcc2` has **26 sellers in total, 24 within 1 km** (haversine; one at 1,015 m and one 10 km away in «آسمان»). Golden seller checks use 24. | The spec's "26 within 1 km" counts every seller of the product; no distance formula puts the 10 km shop inside 1 km. |
| 15 | M1 | Freshness split is fresh 22.8% / recent 34.5% / stale 42.4% / unknown 0.2%. | Consistent with spec §4.1 "58% ≤ 30 d"; the run plan's 26/32/36 split does not add up with that figure. |
| 16 | M2 | Product ranking = pg_trgm **word_similarity** retrieval (GIN, `<%`, threshold 0.4, top 300) + TypeScript rerank: token coverage (exact / model-suffix «t13»≈«t13x» / stem), head-noun match, category, log seller count, budget fit. Category-only queries («گوشی موبایل») switch to popularity ranking. | The spec's `similarity()` weights cannot separate «رم ۶» from «رم ۴» or find «T13x» for «T13»; this passes 15/15 golden queries. |
| 17 | M2 | `routeCategories` is deterministic-first (category votes from the best-matching products + category-name trigram); the fast LLM is called only when the top category's vote share is < 0.6, with a 6 s timeout and rules fallback. | Saves one LLM round-trip per turn on clear queries; routing still works when the provider is down. |
| 18 | M2 | Deterministic budget parser (`lib/search/query.ts`) runs before the LLM: «تا/زیر/حداکثر/حدود/بین … میلیون/هزار/تومن»; spec numbers («۲۰ هزار» میلی‌آمپر، «۲۰ وات»، «تا ۲ کیلومتر») are not budgets. | Reliable «تا ۶۰ میلیون» → 60,000,000 without the LLM. |
| 19 | M2 | With a budget, `search_products` returns in-budget items first and puts the best option ≤ +15% above budget in slot 4 flagged «کمی بالاتر از بودجه». | Matches demo step 1 (A17 128/6 slightly above budget) without hiding in-budget options. |
| 20 | M2 | `pnpm golden` calls the same library functions as `/api/sellers` and `/api/products/search` instead of HTTP. | No running server needed; identical code path. |
| 21 | M2 | Zero-length shifts («00:00–00:00» as a second shift) are ignored when computing open/closed. | They are placeholders in the data and produced «باز است · تا ۰۰:۰۰». |
| 22 | M2 | Seller row adds `lat`, `lon`, `hours_known`, `score_breakdown`, `conditions.{installment,torobpay}_in_person`, `mall.{key,floor_num,unit_kind}`; the LLM sees a compact projection (M3). | Map markers, honest payment-channel labels and «چرا این اول شد؟» need them. |
| 23 | M3 | UI actions (card buttons, «پیگیری ۳ تای اول», …) are user messages with `metadata.action = {tool, input}`; `/api/chat` runs that tool immediately (same code as the LLM's tool call), streams its part, then `streamText` adds 1–2 sentences. Free text goes to the LLM, which picks tools itself. | Cards appear instantly and keep working when the provider is slow/down; the agent still sees the full history. |
| 24 | M3 | Rule-based **offline model** (a custom `LanguageModelV4`, `lib/agent/offline-model.ts`) is used when no API key is configured (or `LLM_PROVIDER=offline`), and per step as an automatic fallback when the provider errors or does not answer within 12 s (middleware in `lib/llm.ts`). The UI shows «حالت آفلاین» / a Persian notice. | No LLM keys were available during the build; Iranian networks often block providers. The spec's "graceful Persian error" is still shown (as a notice) but the chat keeps answering from tool results. |
| 25 | M3 | The ContextBar price chip is a hard seller filter (`filters.max_price`) set only from the BudgetSheet; a budget mentioned in chat is kept as `state.budget` (product search, shown as «بودجه ۶۰ میلیون»). | Otherwise «تا ۶۰ میلیون» silently hides A17 sellers listed at 60.5–61.5M (demo step 3 expects the full list). |
| 26 | M3 | When the ContextBar re-filters a seller list, the new list is written back into the chat history (`setMessages`). | So «چرا این اول شد؟» is answered about the list the user currently sees. |
| 27 | M3 | MapLibre v6 worker is copied to `public/maplibre/` at `predev`/`prebuild` and set with `setWorkerUrl`. | v6 resolves its worker relative to the bundle; Next does not emit it. |
| 28 | M3 | Persian digits in product titles via `faText()` (standalone numbers only; model codes like A17/4G stay Latin). | «حافظه ۱۲۸ رم ۴» reads naturally without breaking model names. |
| 29 | M3 | Buttons are 44px (`h-11`); compact chips keep a 36px look with a `.tap` ::after hit area (≥ 44px). | Spec §9.3 tap targets without a chunky ContextBar. |
| 30 | M4 | Follow-ups are DB rows with a `due_at` (1.5–4 s ahead); `GET /api/followup` resolves due rows idempotently — no `setTimeout` workers. The deterministic outcome is fixed at creation and hidden until due. | Survives restarts, works with several app instances, trivially testable. |
| 31 | M4 | **`SIM_SALT=hamrah-40`**: top-3 sellers of A17 128/4 at the default location (1 km, balanced, demo time Sun 16:00) → confirmed, price_changed, out_of_stock (`scripts/tune-salt.ts`). | Spec §13 step 5 needs mixed outcomes. |
| 32 | M4 | `price_changed` keeps δ ∈ [−5%, +15%] but never \|δ\| < 2%; a quoted price for an offer without a listed price is shown as «قیمت جدید». | A "changed" price equal to the old one after rounding would be confusing. |
| 33 | M4 | Automatic alternatives: when the FollowupBoard sees `out_of_stock`, the client sends an automatic action message (shown as «خودکار: …») that runs `find_alternatives`; the agent then comments. | Replies arrive after the turn that started the follow-ups has ended, so the agent cannot react inside that turn. |
| 34 | M4 | LLM persona transcripts are rejected (template used) if they contain a price other than the simulated truth's. | "Never fabricate numbers" also applies to the simulated seller. |
| 35 | M4 | Purchase checklist: category-family templates offline; LLM version cached per category. | Works without keys; consistent bullets in the demo. |
| 36 | M5 | Visit plan input defaults to shortlist ∪ confirmed/pending follow-ups (never out of stock / no answer); a price change appears in the plan only after «قبول قیمت جدید». | The plan should only send people where the product is (likely) available at an accepted price. |
| 37 | M5 | Dark mode implemented (next-themes, toggle in the header; light by default). | Cheap with the existing tokens; spec lists it as optional. |
| 38 | M5 | `pnpm scenario` (Playwright + system Chrome) is the end-to-end acceptance for spec §13 steps 1–7 incl. a Persian-digits audit; screenshots in `docs/screenshots/`. | One reproducible command instead of manual clicking. |
| 39 | M6 | `/demo-reset` redirects with a relative `Location`. | Behind Caddy, the standalone server's own origin is `0.0.0.0:3000`, not the public host. |
| 40 | M6 | The container entrypoint runs its arguments when given (`docker compose run --rm app node scripts/seed.cjs`), else migrate → auto-seed (`--if-empty`) → server. | Manual reseed without a second image. |
| 41 | M6 | Optional `NPM_REGISTRY` build arg and `POSTGRES_PASSWORD` in `.env`; DB port bound to 127.0.0.1. | Iranian servers often need an npm mirror; the database is not exposed publicly. |
| 42 | M6 | The official dataset URL is not in the repository docs, so the README carries a marked placeholder; DEPLOY.md copies the CSVs with `scp`. | Avoid inventing a download link. |
| 43 | Post-v1 | Sign-in is **name only**: `POST /api/auth/login` upserts `users` by a normalized `name_key` and sets an httpOnly cookie (`hk_uid`, 1 year; `Secure` when `APP_URL` is https). There is no password — typing the same name opens the same chats. | The request was a simple name-only login so chats are kept per user. Fine for a demo and called out in README/DEMO; real accounts would add a password or OTP to the same `users` table. |
| 44 | Post-v1 | A chat is a `sessions` row (`user_id`, `title`, context `state`, UI `messages`). The client creates the chat id and sends it as the `useChat` id, or as `x-chat-id` / `?chat=` to the other APIs; the page URL is `/?c=<id>`. Another user's chat answers 404. | Keeps the per-session state (context, shortlist, follow-ups, plans) unchanged; one id ties chat, ContextBar, follow-ups and plans together; history entries are linkable and survive reloads. |
| 45 | Post-v1 | Messages are saved by the server when a turn ends (`createUIMessageStream` `onEnd`) and by the client (`PUT /api/chats/<id>/messages`, 1.5 s after the reply, ≤ 4 MB) when cards change later (follow-up outcomes, re-filtered seller lists). The model sees the last 16 messages. | The server save makes history independent of the browser; the client save keeps UI state that changes after the turn. 16 messages bound the prompt in long chats. |
| 46 | Post-v1 | Memory is per user and small: usual location (never the default) and radius, last 8 searches, last 5 chosen products. It is updated after each turn and by ContextBar changes, added to the system prompt as a few Persian lines, seeds the location/radius of new chats and drives the hero «از جایی که مانده بودیم». «پاک کردن» clears it. | "Remember me" without embeddings or LLM-written notes that could invent facts: every remembered item is something the user did. |
| 47 | Post-v1 | Desktop layout from 1024 px: history sidebar · chat · map column, each scrolling on its own; card grids use container queries (`@container`, `@2xl:`) instead of viewport breakpoints. Phones keep one column with sheets. | The chat column's width, not the viewport, decides whether two seller cards fit side by side; one component tree serves both layouts. |
| 48 | Post-v1 | Every shop within the radius is drawn in one GeoJSON circle layer (`/api/shops/near` returns compact tuples; colour = lists the chosen product / activity category only / other); the seller list stays numbered DOM markers. Layers are added on `style.load` with a ready queue. | Thousands of DOM markers are slow on phones, one WebGL layer is not. `load` waits for tiles, which left the map blank on slow networks. |
| 49 | Post-v1 | `set_context` ignores «نزدیک من / من / اینجا…» and the current location's own label; the system prompt says «نزدیک من» means the current location. | A live model called `set_context(location_text:"فردوسی")` for «نزدیک من», which moved the centre and widened the list to 4.6k shops. |
| 50 | Post-v1 | The end-of-turn save never replaces a resolved follow-up status with pending/contacting, and the visit plan reads follow-up rows directly. | The turn that starts follow-ups ends before they resolve; its save raced the poller and the plan listed an out-of-stock shop as «در حال پیگیری». |
| 51 | Post-v1 | `faText` is applied to all LLM-authored text (assistant messages, checklist items, transcripts). | Live models write ASCII digits («حافظه 128»); the UI rule is Persian digits everywhere. |
| 52 | Post-v1 | `/api/me` answers 200 `{user:null}` when signed out. | Browsers log a 401 as a console error, and being signed out is a normal state. |
| 53 | Post-v1 | The Google model in `llm-check` and the docs is `gemini-3.1-flash-lite`. | `gemini-2.5-flash` is no longer offered to new API users; `gemini-3.1-flash-lite` passes the tool-call check in ~4 s. |
| 54 | Post-v1 | Shop type for the map = 20 types (`lib/data/shop-types.ts`) derived from the ~4,000 flat activity categories by ordered keyword rules (`lib/data/shop-type-rules.ts`, word-boundary matches, ambiguous categories vote with weight ½ or not at all); a shop's type is the majority vote over its categories, else over the categories of the products it lists (weighted by offers). 92 % of category memberships get a vote (`pnpm tsx scripts/shop-types-report.ts`). The 1,797 shops with neither are «فعالیت ثبت نشده»; shop names are not used because they are synthetic in the dataset. | The dataset has no category hierarchy; rules are explainable and testable, and unknown stays unknown instead of being guessed. |
| 55 | Post-v1 | Types are computed in the app for all shops at first use and cached for an hour (`lib/search/shop-types.ts`), not stored by the seed. | Works on databases that are already seeded (`AUTO_SEED` skips a loaded DB); ~0.6 s once per hour. |

| 57 | Post-v1 | Type chips with counts filter the shop layer client-side (`setData` re-clusters); while a type is selected, cluster pills show that type's glyph. On phones the legend opens from a «راهنما» button. | Instant filtering without a request; the 320 px phone map stays readable. |
| 58 | Missions | Compound requests run through a mission layer: rule-based extraction first (`lib/agent/mission/extract.ts`: budget, place, conditions, delegated checks, plan/top-N, intent), then the fast LLM (`generateText` + `Output.object`, the v7 form of `generateObject`, 5 s) fills the product words and gaps; rules win on numbers, place and checks they found. `runMission` executes deterministically with the same services as the tools. | Numbers and places must not depend on the model; the LLM is good at «which words are the product». Works offline. |
| 59 | Missions | In `mode: 'auto'` (always sent by the client) the chat route detects a mission with the rules and **runs `run_mission` directly** (the existing UI-action path), then the model writes ≤ 3 sentences. The spec's system hint alone was not used as the only mechanism; the tool is still offered to the model and the prompt names the trigger words for messages the rules miss. | The failing example showed the model does not reliably carry out multi-goal requests; direct execution also works when the provider is down. |
| 60 | Missions | A message is a mission when it has ≥ 2 goals (find, place, conditions, checks, plan/compare) or delegates a check («خودت بپرس»، «چک کن»، «پیگیری کن»، «ببین باز هستن»، «مطمئن شو»، «زنگ بزن») and there is a product to act on (named now or chosen earlier). Budget and intent modify «find»; «فقط اونایی که الان بازن» alone is a condition (normal path); `«گوشی سامسونگ تا ۶۰ میلیون نزدیک من»` stays the normal four-step flow. | Keeps the demo flow and single requests unchanged; avoids hijacking follow-up questions. |
| 61 | Missions | «حدود/تقریباً/دور و بر/حوالی X» (and a bare «X میلیون») is a ±10 % band in missions (45–55 M for 50 M); the parser also understands «از X تا Y» (range), «از X به بالا / حداقل / بالای» (min) and «حدود قیمت X». The normal product search keeps its −20 %/+10 % band (#19). | Spec band for missions without changing the golden search behaviour. |
| 62 | Missions | Places: a static gazetteer of 117 Tehran neighbourhoods/squares/landmarks (approximate centroids, ±500 m) + the 30 dataset labels (shop centroids) + malls. Keys ignore spaces/ZWNJ and «آ»/«ا» (سعادت آباد = سعادت‌آباد = سعادتاباد); fuzzy trigram ≥ 0.45; common-word names («آزادی»، «انقلاب»…) need a marker; «بازار تجریش» is the mall, bare «تجریش» the neighbourhood. `set_context` and the location sheet use it; a mall sets a 300 m radius. | «سعادت آباد» was not among the 30 labels, so the agent could not place the user. No external geocoder. |
| 63 | Missions | Coverage loop: radii [requested, 1, 2, 3, 5, 8 km] until ≥ 3 sellers; the report states plainly when the requested area has none (with the nearest seller's distance and nearest place name) and offers «مرکز شهر را هم ببین» when far from the centre. Rows only come from offers. | 85 % of shops are in the centre; around سعادت‌آباد there is 1 Samsung-phone seller within 8 km — the honest answer is the note, not invented sellers. |
| 64 | Missions | `findSellers({ price_band })` picks each shop's offer **inside the band first** (only when a band is given). | The one shop near سعادت‌آباد lists A07 64/4 at 44 M and A07 128/4 at 48 M; the cheapest-first rule hid the in-band offer. |
| 65 | Missions | For generic requests (no model code) the seller search adds up to 30 similar in-band models when the top 4 have < 3 sellers; «A17» stays exact. | Users asking for «پاوربانک ۲۰ هزار» do not mean the four specific models the ranking put first; deviation from "keep top 3–4" for the seller step only. |
| 66 | Missions | When nothing is found, a probe at the widest radius names the blocking constraint — the budget band and/or a condition — with a one-tap chip («بدون محدودیت بودجه», «بدون این شرط‌ها»); filter relaxations from `findSellers` are used first. | «پاوربانک ۱–۲ میلیون قسطی، تجریش»: power banks near Tajrish cost 4–10 M; saying only «nothing found» would hide why. |

| 68 | Missions | Verdicts: recommended = in band ∧ (confirmed ∨ fresh price) ∧ not closed; avoid = out of stock ∨ suspicious price ∨ closed with no opening later today (`opensAt` added to seller rows); unknown = unconfirmed and stale/undated; otherwise ok. | 69 | Missions | Progress is a `data-mission-progress` UI stream part (same id, updated in place), emitted before extraction and after each step, shown above the report and collapsed when done. | Live «📍 → 🔎 → 🏬 → 📨 → ✅» feedback during the ~3–8 s run. |
| 70 | Missions | Chip edits: × on an understood constraint re-runs the mission without it (overrides stack: `drop`, `radius_m`, `location_text`); no free-form editor. | Simple, predictable edits; the composer is there for anything else. |
